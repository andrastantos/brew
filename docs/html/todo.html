Multiple Load-Stores

This is a new idea that I’m toying with: would it be too difficult to add a pair of (multi-cycle) instructions that could load and store any combination of registers? This goes against the RISC approach, it’s clearly a complex concept. However, ARM has it and for good reason: it collapses function prologs and epilogs, results in very compact code and - if implemented properly - results in pretty nice memory access patterns with high efficiencies. I have found a right-sized hole in the instruction space to fit these instructions in, but the implementation complexity is rather high. I’m not yet sure if it’s worth to have them, I probably need to model it first.

Open items from the toolchain work (as of 2026-11-27)

Collected from the toolchain bring-up (GCC 16 and trunk, binutils/gdb and newlib merges, Espresso tuning). The workspace CLAUDE.md has the measurements and commit references behind each item.

Espresso performance

Todo

Fetch page size. The fetch unit ends bursts at 256-byte boundaries (page_bits = 7, counted in 16-bit words), but the external bus allows bursts within a 512-byte DRAM page. On the cycle model, 512 bytes halves the average cost of page ends (+0.30% to +0.16% against no page effects over the code-generation tests); 1024 bytes adds little. Confirm that every supported DRAM configuration has at least 512-byte pages, then change page_bits (RTL, cycle model, regenerated Verilog, rig suite).

Todo

Remaining Espresso cycle budget at -O2: ~43% refills after taken branches, ~16% fetch starvation, ~10% register waits. Ideas not yet evaluated: ending bursts early at fetched branches (the RTL’s break_on_branch_early option, currently off), cheaper restarts after a taken branch, and the cost of the 3-cycle result latency.

Todo

Branchless selects don’t pay on Espresso without a conditional move or set-on-compare (a branch over a move costs 3-5 cycles, a mask select 4-9 cycles and more on a full compare). Revisit if the ISA gains a select instruction, or once the scheduler can overlap independent select chains.

Todo

Loop unrolling and peeling gain 3-5% cycles at 6-30% more code and are left to users (-funroll-loops, -fpeel-loops). Decide whether a capped default makes sense for -O2.

Todo

The cycle model does not cover DMA, interrupts, exceptions beyond a taken branch, CSR wait states, or the timing of cores without a multiplier or shifter.

Cores without a multiplier or barrel shifter

Todo

Performance of the reduced variant is unmeasured. Shifts call __brew_ashl/__brew_ashr/__brew_lshr (one loop iteration per bit), multiplications __mulsi3. Measure on the cycle model, then consider faster routines (fewer iterations for common counts), inline loops, and expanding constant right shifts better.

Todo

Only one reduced library variant exists (min/: neither unit). A core with only one of the two units links with it too; separate nomul and noshift multilibs would let it use the unit it has.

Todo

13 libstdc++ tests time out on the reduced variant (special functions, to_chars, random distributions). Either raise the time limit for that board or accept them as known.

ABI decision: PREFERRED_STACK_BOUNDARY is 32 bits. 64 or 128 would make alloca results 8-aligned (gdb.base/eh_return.exp) and over-aligned locals cheaper, at the cost of stack space; it changes the ABI.

Todo

Decide whether to move _stack down (e.g. 4 KB), and update those tests’ xfail comments either way.
